The time I was blocked on a simple problem

I was working on a small coding task. I was trying to make a button do something when clicked. I’ve done similar thing before, so I thought this would be quick. But when I clicked the button nothing happened. I double-checked the code, rewrote it a few times and still couldn’t figure it out. I felt stuck and annoyed. I tried a few things - googled the problem compared my code to examples and console.logged everything and eventually just stepped away for a bit. When I came back and looked again, I saw that I had misspelled the name of the function I was trying to call. One small typo. I fixed it and it worked. I felt stupid but also relieved. I learned that sometimes the problem is small and I just need to slow down and not panic. Taking a break actually helped me notice the mistake. Now I always double-check names and spellings before digging into something bigger.

The time I elegantly solved a problem

I was working on a page layout in HTML and CSS. The text was overlapping with an image when the screen size got smaller. At first, I thought I’d need to rewrite a lot or use media queries everywhere. It felt like it was going to be messy. But then I stopped and looked at the structure more closely. I realised the issue was caused by using fixed widths and not letting elements grow or wrap properly. So I switched to using flexbox and added flex-wrap: wrap; along with some percentage-based widths. Then I saw the layout adjusted nicely at different screen sizes, without needing an extra code. It felt really satisfying to fix it in a clean, efficient way. Now I realise that stepping back and understanding the structure can lead to a simpler and more elegant solution.

Here's a reflection on how confident I feel using each of problem-solving techniques/processes

Pseudocode
I’m still getting used to it. Sometimes I forget to use it, but when I do, it actually helps me organise my thoughts and understand what I want the code to do. I want to get more consistent with it.

Trying something
This I do a lot. Sometimes too much. It helps me explore and notice what works and what breaks. I’m learning to mix it with more structure.

Rubber ducky method
I don’t always use this formally, but I notice that when I try to explain the problem (even just in my head or to ChatGPT), I often spot the issue. I think it’s a helpful method.

Reading error messages
Getting better at this. At first they looked scary and confusing, but now I’m starting to slow down and actually read what they say. It’s never clear, but it gives me clues.

Console.logging
I do this a lot. It helps me understand what’s going on inside my code step by step. I feel pretty confident using it.

Googling
Very confident here. I use it all the time. For errors, syntax, examples, anything. But I’m also trying to be smarter about how I search and how I read the answers.

Asking your peers for help
I feel confident asking for help. I haven’t used it much so far because I’ve been able to solve things by Googling. I always think - Maybe I should try to figure it out myself first. But I’m sure that as things get harder, I’ll start asking for help more often.

Asking coaches for help
I’m getting more comfortable with this. I realise it’s a good way to learn faster. Especially when I feel completely stuck.

Reflection on a time I was reluctant to ask for help.

To be honest, I haven’t really felt reluctant to ask for help. I know that learning to code is challenging, and I don’t expect myself to know everything right away. When I get stuck and can’t find the answer by Googling or testing things, I’m okay with reaching out.
I think what helps is knowing that everyone’s learning too, and there’s no pressure to be perfect. Everyone have been really supportive, so I don’t feel judged when I ask questions. If anything, I feel like I learn faster by asking and discussing things.
